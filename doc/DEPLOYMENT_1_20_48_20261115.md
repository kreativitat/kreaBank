## Failed checks and source findings

1. **Strict exact-total enablement failed.** The shared supplier script enables
   confirmation with a one-cent difference. A larger mismatch is rejected.
   This tolerance already existed in 1.20.47; the unchanged server normalizer
   also adjusts the last product line for differences up to one cent. No invoice
   was submitted to exercise that behavior on production.
2. **Mobile supplier-dialog layout failed.** At a 390 px viewport, the dialog is
   372 px wide but its product table is approximately 709 px wide, producing
   horizontal overflow in the overlay. The compact responsive styles require a
   `.kb-recon` ancestor; the new row dialog is under `.kb-worklist`.
3. **Pinned version metadata is inconsistent.** The descriptor and About report
   1.20.48, but the pinned `VERSION` file still contains 1.20.47. It was preserved
   to keep the deployment byte-identical to the requested source.
4. **Basic inline creation has a review gap.** `more_entry` binds its expiring
   single-use review to the source key, then loads the current source amount on
   submission. It does not compare the source facts displayed at review time;
   changed evidence can therefore differ from what was reviewed. This was found
   by source inspection and was not tested through a live financial submission.

These findings remain in the requested release. No unpinned runtime patch was
installed. The native-transfer query/audit failure behavior documented in the
[previous deployment](DEPLOYMENT_1_20_47_20261115.md) is also unchanged.

## Separately approved duplicate correction

Before deployment, the owner approved one specific duplicate case and confirmed
its fiscal period was open. The correction used the existing History undo
service, shared explicitly reviewed existing-movement reconciliation and native
`AccountLine::delete()` with triggers enabled. All operations committed in one
outer native database transaction, with current ownership, permissions, exact
facts, claims, payment, accounting, cheque and fiscal protections checked.

Ordinary History undo does not delete a quick-entry-created movement. The
supported sequence therefore rebound the debit statement line to its existing
transfer leg before deleting the released, unclaimed duplicate through the
native class. The credit statement line was reconciled to the existing reciprocal
leg. One duplicate movement was removed, two imported lines were reconciled and
the three expected module audit events were verified. No private orchestrator
issued direct financial SQL writes.

Independent post-commit evidence verified the exact affected balance/count
changes and unchanged hashes for all unaffected rows across 48 financial tables.
The native movement list showed the transaction once. All other review cases
were left unchanged. Historical quick-entry evidence and its pending import
metadata remain retained; the original import hash remains reserved. Private
before/after evidence and the owner's report contain the exact identities and
amounts; they are excluded from this public record.

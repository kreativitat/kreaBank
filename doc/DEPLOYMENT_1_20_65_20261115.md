[`e69f0cf`](https://github.com/kreativitat/kreaBank/commit/e69f0cf51fae0f14d2a3cfc017be15c4856b3f24).

## Result

Customer-transfer enrichment preserves the complete original native reference
text and appends missing verified invoice references once. Receipt details no
longer suppress previously eligible manual advice. Existing scores, the 35-point
ambiguity guard, exact amounts, visibility, owner-company checks and unattended
matching remain unchanged.

Scalar payment-difference Undo now invalidates the exact native movement,
restored invoice, removed payment and restored full invoice amount. The immutable
audit has no invoice date, so the restored-amount cache footprint covers all dates
in the existing bounded scan. Unaffected amounts/currencies and progress remain
cached. Malformed Undo evidence fails before service execution.

## Production end-to-end acceptance

An authenticated internal-browser session in another owner company reviewed an
existing incoming transfer receipt with a fully paid invoice allocation and the
same owned bank account, amount and booking day. The list displayed its native
receipt reference, actual shared customer and invoice count. The final signed
manual reconciliation was submitted once through the normal list button.

Read-only before/after evidence verified:

- The same existing receipt, paid invoice, allocation, native bank entry and bank
  links were reused. All payment/allocation/bank counts stayed identical.
- Only the expected bank reconciliation flag, statement reference, actor and
  modification timestamp changed. Source amount/date/evidence stayed unchanged;
  its status/allocation/native mapping became reconciled.
- Exactly one source mapping and one new audit exist; no group, aggregate bank
  movement, new payment or invoice allocation was created. Other same-day bank
  entries and imported lines remained identical.
- The access log contains exactly one confirmation POST and its canonical return
  GET. There was no analysis POST, refresh link, reload loop or restarted search.
  Unaffected pending rows retained their previous results.
- Reconciled view showed the completed receipt and its reviewed Undo control.
  Cancelling that dialog preserved every financial/reconciliation record. Earlier
  production Cancel, X and Escape tests generated zero list requests and restored
  focus; no Undo was submitted in production.

About displayed 1.20.65. Desktop and 390 px list checks retained native navigation,
correct column alignment, responsive table scrolling and no console errors.
The statement tabs visibly filtered distinct pending/reconciled populations;
History displayed every batch payment beside its exact bank movement. The UI
reference is the installed Dolibarr 24 documentation and established native list,
History and correction-dialog components. Detailed business identifiers, complete
snapshots, access-log evidence and screenshots remain private.

## Deviations and limitations

The first staged server-check transport exited without a diagnostic although its
complete result file reported all 73 commands passing. The unchanged checks were
rerun successfully before installation. Later SSH proxy failures prevented a
readback connection; the existing authorized direct SSH key restored access.
No authentication or server setting was changed. An early verification assertion
was corrected to include Dolibarr's expected reconciliation-actor field.

The original 1.20.64 acceptance findings are documented in its deployment record;
1.20.65 resolved them before financial metadata approval. No fictitious payment,
bank movement, fee, customer alias or allocation was introduced to force a match.
Replay and actual Undo were exercised only on disposable data;
production retained the approved reconciliation.
